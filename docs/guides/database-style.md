# Database Style Guide

Read ADR-0007 (Flyway) and ADR-0008 (user-scoped access) first.

## Migrations

- Location: `backend/src/main/resources/db/migration`
- Name: `V<n>__<snake_case_description>.sql` — `V7__add_recurring_transactions.sql`
- **Append-only.** A merged migration is frozen forever. Fix mistakes with a new migration.
- One logical change per migration. Reviewable in isolation.
- Plain SQL. Reviewed like code, because it is.
- Destructive steps (`DROP COLUMN`, `DROP TABLE`) get an explicit comment saying why the data
  is safe to lose, and they are separated from the deploy that stopped writing the column.

Hibernate runs `ddl-auto: validate` everywhere. If startup fails on a schema mismatch, the fix
is a migration — never a change to `ddl-auto`.

## Naming

| Thing | Convention | Example |
|---|---|---|
| Table | plural, `snake_case` | `transactions` |
| Column | `snake_case` | `posted_at` |
| Primary key | `id` | |
| Foreign key column | `<singular>_id` | `account_id` |
| Foreign key constraint | `fk_<table>_<ref>` | `fk_transactions_account` |
| Unique constraint | `uq_<table>_<cols>` | `uq_users_email` |
| Check constraint | `ck_<table>_<rule>` | `ck_transactions_amount_scale` |
| Index | `ix_<table>_<cols>` | `ix_transactions_user_id_date` |

Never reserved words as identifiers (`user`, `order`, `end`). The legacy app used a table
literally named `user`, which needs quoting everywhere. Use `users`.

## Column rules

- **Primary keys are UUIDs** (`uuid` type), generated by the application. Sequential integers
  leak volume and let anyone enumerate other people's rows by incrementing a URL.
- **Money is `NUMERIC(19,4)`** with a `CHECK` constraint on scale where it matters. Never
  `float`, `real`, or `double precision` — ADR-0006.
- **Timestamps are `timestamptz`**, stored in UTC. Never `timestamp` without a zone.
- **Dates that are genuinely dates** (a transaction's date, a budget period) are `date`.
  A purchase happened on a day, not at an instant in a timezone.
- `NOT NULL` unless nullability carries real meaning. "Unknown" and "empty" are different;
  don't use `NULL` for both.
- Every user-owned table has a `user_id` foreign key. Not "reachable via a join" — a direct
  column, so the ADR-0008 scoping predicate is always one condition.
- `created_at` and `updated_at` on every table. The legacy app had neither, and it cost.

## Constraints belong in the database

The application validates for good error messages. The database enforces truth.

```sql
ALTER TABLE transactions
  ADD CONSTRAINT ck_transactions_amount_scale CHECK (scale(amount) <= 4);
```

Foreign keys, unique constraints, and checks are not optional because "the app already checks".
The app has bugs; the constraint is the backstop.

## Indexes

- Index every foreign key. Postgres does not do this for you.
- Index the columns you actually filter and sort on — and because of ADR-0008 that almost always
  means a composite index leading with `user_id`: `(user_id, date DESC)`.
- Partial indexes for sparse predicates: `WHERE archived = false`.
- Don't index speculatively. Every index costs write throughput.

## Queries

- Spring Data derived queries or `@Query` with **named parameters**. Never string concatenation.
- No native SQL unless a JPQL version is genuinely impossible; when you must, parameterize and
  comment why.
- Watch for N+1. Use `@EntityGraph` or an explicit `join fetch`. A list endpoint that issues one
  query per row will not be found by a unit test — check the query count in an integration test.
- `ORDER BY` fields come from an allowlist enum. A sort parameter interpolated into a query is
  SQL injection with extra steps.

## Deletes

- Soft-delete (`archived_at`) for anything a user might want back — accounts, categories.
- Hard-delete where retention is a liability.
- Deleting a user removes or anonymizes everything they own. No orphaned financial rows, ever.
